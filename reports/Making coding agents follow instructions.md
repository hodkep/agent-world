# Put rules in context, enforce with hooks

Coding agents follow an instruction reliably only when it is already in context at the moment of decision, short, and specific. They follow it unreliably when the model must first decide to go and get it. The evidence for this is consistent across vendors, practitioners and academic work, though almost all of it is small-sample and Claude-centric. Anthropic's own documentation says CLAUDE.md is "context, not enforced configuration" with "no guarantee of strict compliance" ([Claude Code memory](https://code.claude.com/docs/en/memory)), and its June 2026 blog says a real guardrail "needs to be deterministic", meaning hooks and permissions ([Claude blog](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)). Skills trigger by model judgment and often do not trigger: Vercel's eval found a skill never invoked in **56% of cases** while an always-loaded index scored **100% against 53% for the skill** ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). Your Haiku 4.5 cells (always-on rule 3/3, MCP-fetched skill 1/4, native plugin skill 0/4, pointer-only reminder 0/4, content-carrying reminder 4/4) match this pattern, and the only contrast that is statistically separable at those sample sizes is 4/4 against 0/4. Hooks that inject content or block actions are the best-supported levers. Gemini CLI and agy have equivalent hook mechanisms, but the evidence for agy specifically is thin. Several things your library will lean on are unmeasured: hook-injected reminders at scale, Stop-hook gates, agy per-turn injection, and any model other than Haiku 4.5.

## Why rules decay: advisory delivery, competing text, and long contexts

Two separate mechanisms make instructions fail, and they need different fixes. The first is delivery status. Claude Code sends CLAUDE.md as a user message after the system prompt, not as part of it ([memory docs](https://code.claude.com/docs/en/memory)), and an unresolved bug report from September 2025 says the wrapper text told the model the context "may or may not be relevant" ([anthropics/claude-code #7571](https://github.com/anthropics/claude-code/issues/7571), closed "not planned"; wrapper text may have changed since). Anthropic concedes that contradictory rules are resolved arbitrarily and that user-level and project-level files that conflict get either one followed ([memory docs](https://code.claude.com/docs/en/memory)). Your own global rules plus project rules are exactly this setup. Users report violations even with MUST, NEVER or "HARD RULE" wording, for example [#34197](https://claudeissues.com/issue/34197-bug-claude-code-continually-ignores-claude-md-file), but these are unverified anecdotes, including the "~50% of sessions" figure. Gemini CLI has the same pattern: issues report agents committing, pushing or editing against explicit GEMINI.md prohibitions, and the agent itself proposed git pre-push hooks as a physical safeguard ([gemini-cli #24387](https://github.com/google-gemini/gemini-cli/issues/24387); issue numbers came through a summarizer and need direct checking).

The second mechanism is degradation as context grows. The best-controlled study is "LLMs Get Lost in Multi-Turn Conversation": across 15 models and 200,000+ simulated conversations, multi-turn performance fell on average **39%**, with strong models going from about 90% to about 65%. The loss was mostly unreliability (the gap between best and worst runs rose **112%**) rather than lost aptitude (about 16%), and models that committed to a wrong assumption early did not recover ([arXiv 2505.06120](https://arxiv.org/html/2505.06120v1)). That is the signature you would expect of a rule that works in a demo and fails in some fraction of long sessions. Instruction density also matters: on IFScale the best of 20 models reached only **68% at 500 instructions**, and earlier instructions were followed better than later ones ([arXiv 2507.11538](https://arxiv.org/abs/2507.11538)). Chroma's 18-model study found input length alone makes performance "increasingly unreliable", and, counterintuitively, a coherent haystack hurt more than a shuffled one ([Chroma](https://www.trychroma.com/research/context-rot)); a long agent transcript of plausible tool output is exactly that kind of distractor. Anthropic states the same mechanism qualitatively and gives no curve ([Best practices](https://code.claude.com/docs/en/best-practices)). The caveat is that none of these studies measures rule compliance by a 2026 coding agent. They are tests of retrieval, constraint satisfaction or multi-turn QA, and the step to "your TDD rule drifts" is an inference.

The size guidance that follows is mostly Anthropic's heuristic, not a measured threshold: keep each CLAUDE.md under **200 lines** because "longer files consume more context and reduce adherence", and test every line against "would removing this cause Claude to make mistakes?" ([memory](https://code.claude.com/docs/en/memory), [best practices](https://code.claude.com/docs/en/best-practices)). Imports with `@path` do not reduce cost because they load at launch. Secondhand reports put the best range at 100 to 150 lines (Augment, not traced to a primary source). The ETH Zurich study adds that LLM-generated context files changed success by **-0.5% to -2%** and raised cost 20 to 23%, while human-written minimal files gave about +4%, though agents did follow tool instructions in the file (a mentioned tool was used 1.6 times as often as an unmentioned one) ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)). Antigravity's limits are a hard 24 KB per rule file and a 20,000-token budget across global and always-on rules ([Antigravity Rules](https://antigravity.google/docs/rules)); Codex caps combined AGENTS.md at 32 KiB by default (secondary source). Your own global file is long, carries "HARD RULE" language, and sits on top of project files, which is the profile Anthropic's docs flag. Anthropic also says that on current models aggressive emphasis can over-trigger and recommends emphasizing at most one or two lines ([prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)), although its skill-authoring guide still suggests "MUST" when a rule is missed; the two docs disagree.

## Skills and on-demand tools are skipped unless the harness removes the choice

Skills are a model-judgment mechanism by design. Only name and description sit in context; Claude "relies on judgment about relevance" to load the body ([Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)). Anthropic offers no trigger-rate guarantee. Its sanctioned deterministic routes are explicit `/skill-name` invocation, preloading skills into a subagent through the `skills:` field, an `@agent` mention, or a hook that injects the instruction ([skills](https://code.claude.com/docs/en/skills), [sub-agents](https://code.claude.com/docs/en/sub-agents)). Descriptions are truncated at 1,536 characters in the Claude Code listing and every listed skill costs context on every turn. Gemini CLI and agy use the same pattern: names and descriptions in the system prompt, the model calls `activate_skill` or reads the file when it judges it relevant ([Gemini CLI skills](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/cli/skills.md), [Antigravity skills](https://antigravity.google/docs/skills)).

The measured activation rates are low without help and move sharply with the harness. In Scott Spence's synthetic API test on Haiku 4.5 (50 tests), a simple instruction hook activated skills **20%** of the time, a forced "evaluate every skill YES/NO" hook **84%**, and an LLM-classifier hook 80% ([Spence](https://scottspence.com/posts/how-to-make-claude-code-skills-activate-reliably)). Against the real Claude Code binary with Sonnet 4.5 (22 cases, 2 runs), no hook scored 55% and 50%, the forced-eval hook **100% and 100%**, but on 24 harder prompts forced-eval fell to 75% (with 5/5 true negatives) and the LLM-classifier hook produced 4 false positives in 5 negative cases, at about 2 seconds extra latency for forced-eval ([Spence sandboxed evals](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)). The author notes the synthetic and real-binary numbers differ, so no rate quoted without its harness is portable. A keyword hook that merely suggested a skill got 4 to 5 of 10 ([Spence](https://scottspence.com/posts/claude-code-skills-dont-auto-activate)). Vercel's result is the cleanest single contrast: skill default 53% (identical to no skill), skill plus an explicit "use it" instruction 79%, and an 8 KB index in always-loaded AGENTS.md 100%, with wording changing behavior ("You MUST invoke the skill" made agents read docs first and miss project context). Academic work agrees in direction: the 2026 Skill-Use preprint finds trigger and compliance are independent failure points and use is conditioned on the harness more than the model, with the best configuration scoring 0.613 ([arXiv 2608.04828](https://arxiv.org/abs/2608.04828), details unverified because the PDF was unreadable). Another 2026 paper finds that retrieving a skill does not guarantee benefit ([arXiv 2609.00549](https://arxiv.org/abs/2609.00549)).

Your cells line up with these. The pointer-only reminder (0/4) resembles Spence's "simple instruction" or "gentle reminder" arm, which did poorly; the content-carrying reminder (4/4) removes the fetch step entirely, as the Vercel index does; and the 1/4 MCP fetch and 0/4 native plugin skill are the "model must decide to go get it" condition. The native plugin skill scoring below the roughly 50% no-hook baselines in Spence's Sonnet runs is unexplained, and with 4 prompts it cannot be separated from them, so the likelier explanations are Haiku 4.5 being weaker at this, prompt wording that did not match the description, or a harness artifact. Do not conclude that plugin skills are worse than MCP-fetched ones. For an MCP fetch tool, Anthropic's tool guidance says the description is "by far the most important factor", and refinements have produced large gains ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools), [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)), so a fetch tool with a thin description is a confound in your 1/4. Forcing a tool call through `tool_choice` is not available as a fix here: Anthropic says it blocks pre-tool text and invalidates cached message blocks, and per its docs the current Sonnet 5.5, Opus 5.5 and Fable 5.1 return a 400 for `any` or `tool`. Inside Claude Code the model is on `auto` regardless. Gemini's API has an `any` mode, but no coding-agent harness was found exposing it ([Gemini function calling](https://ai.google.dev/gemini-api/docs/function-calling)).

## Hooks and placement are the levers with real support

Hooks are the only deterministic layer, and Anthropic's docs describe them in those terms: "An instruction like 'never edit .env' in CLAUDE.md or a skill is a request, not a guarantee. A PreToolUse hook that blocks the edit is enforcement" ([Best practices](https://code.claude.com/docs/en/best-practices)). The hook surface in Claude Code ([Hooks reference](https://code.claude.com/docs/en/hooks)) has three tiers relevant to you. First, injection: SessionStart (with a `compact` matcher, which re-injects after compaction) and UserPromptSubmit add stdout or `additionalContext` as a system reminder, capped at **10,000 characters** per string, with a 30-second default timeout on UserPromptSubmit. Delivery is deterministic, but whether the model obeys the injected text is still the model's decision. Second, blocking: PreToolUse can deny (exit 2 or `permissionDecision: deny`), rewrite input with `updatedInput`, and deny beats allow when hooks disagree. Third, completion gates: a Stop hook can block the turn from ending and feed a reason back, bounded by an **8 consecutive continuation cap** (resets when a tool is called) and the need to check `stop_hook_active` to avoid loops. Anthropic also documents `/goal` and a fresh-context verification subagent as alternatives, and notes a reviewer asked to find gaps will usually report some even when work is sound.

The strongest evidence for injection comes from your own cell plus Spence and the recap literature. The 4/4 content-carrying reminder is consistent with Spence's forced-eval results, and recency has independent support: restating all requirements in the final turn lifted multi-turn performance from about **50% to 67%** and repeating prior information each turn gave 62%, still below the roughly 90% single-turn ceiling ([arXiv 2505.06120](https://arxiv.org/html/2505.06120v1)); periodic re-prompting added about 16 points on long-document QA with GPT-4 Turbo and Claude 2.1 ([R&R, EMNLP Findings 2024](https://arxiv.org/html/2403.05004v1)). Both are non-coding tasks on older models, so they support the direction, not the size, of the effect for your app. Anthropic's long-context guidance (queries and instructions after long data, up to 30% better in its tests) and Google's identical advice point the same way ([Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), [Google](https://ai.google.dev/gemini-api/docs/prompting-strategies)). The Manus "recitation" pattern of rewriting a todo file each step is the same idea, with no published ablation ([summary](https://agentic-ai.readthedocs.io/en/latest/ContextEngineering/manus/)). Per-turn injection also has costs: tokens land in context every turn, and Anthropic's Sonnet 5.5 guide warns that harness text injected after every tool result can be read as prompt injection and reminders should be kept infrequent ([Sonnet 5.5 guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)). Nobody has published token-cost or compliance data for per-turn reminders over long sessions.

On process orchestration, the evidence ranks enforcement strength, not outcomes. Prompt-only systems (Superpowers' SessionStart bootstrap, Spec Kit templates) inherit the activation problem; Kiro adds approval gates; AWS AI-DLC v2 adds an engine with state, approval gates and an audit trail ([aidlc-workflows](https://raw.githubusercontent.com/awslabs/aidlc-workflows/main/README.md), [Kiro](https://kiro.dev/docs/specs/index)). Thoughtworks' hands-on review found agents "frequently ignored instructions" in specs and that the ceremony is heavy for small tasks ([Böckeler](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). No controlled comparison of quality, cost or autonomy exists for any of these tools, so engine-level determinism is supported by mechanism (the harness decides what the model sees and what may happen next), not by outcome data. ToolFailBench's finding that even the best model has a clean tool-use rate of only 86% and shows result-ignoring and fabrication modes supports harness-enforced verification over model-optional verification ([arXiv 2607.04686](https://arxiv.org/abs/2607.04686), mostly older and open-weight models).

## Claude Code and agy differ in documentation depth, not in kind

The two agents share the same architecture and the same weaknesses. Both load rule files into every turn, both use progressive-disclosure skills triggered by model judgment, and both have hooks. Gemini CLI concatenates global, workspace and just-in-time GEMINI.md files and sends them "with every prompt" ([GEMINI.md docs](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/cli/gemini-md.md)); Antigravity adds four rule activation modes (`always_on`, `model_decision`, `glob`, `manual`), reads AGENTS.md and GEMINI.md, and caps files at 24 KB. Claude Code reads AGENTS.md only when no CLAUDE.md exists, unless configured otherwise, and Anthropic's suggested pattern is a CLAUDE.md that imports `@AGENTS.md` ([memory](https://code.claude.com/docs/en/memory)). Note that a `model_decision` rule has the same weakness as a description-triggered skill, as Cursor's "Apply Intelligently" mode presumably does; neither was measured.

On hooks, Gemini CLI's `BeforeAgent` appends `additionalContext` to the user prompt for that turn, which is the direct analogue of UserPromptSubmit, and `BeforeTool` can deny; exit 2 blocks in both ([Gemini hooks reference](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/hooks/reference.md)). agy uses `.agents/hooks.json` with PreToolUse, PostToolUse, PreInvocation, PostInvocation and Stop events, regex matchers, a 30-second default timeout, and allow, deny, ask or force_ask decisions ([Antigravity hooks](https://antigravity.google/docs/hooks)). What the notes could not establish for agy matters most for you: whether PreInvocation can add context rather than only observe, the output schema for context injection, where rules sit relative to the system prompt, ordering among GEMINI.md, AGENTS.md and `.agents/rules`, and any measured adherence. Gemini CLI also lets you replace its system prompt entirely with `GEMINI_SYSTEM_MD`, which Claude Code answers only partly through `--append-system-prompt` ([system prompt docs](https://geminicli.com/docs/cli/system-prompt/)). The Claude side has first-party measurement tools (`claude plugin eval` with a `tool_used: Skill` grader, `/skill-doctor`, `InstructionsLoaded` hook, `/doctor prompt-audit`) with no agy counterpart found. Everything agy-specific in the notes comes from thin or redirecting docs, and several details come from secondary sites that contradict the official ones (a 12,000-character limit claim against the official 24 KB).

## Recommendations for Agent World (judgment, not findings)

These follow from the evidence above and your cells, and each carries the evidence strength noted.

**Always-on.** Keep a small core, ideally a few dozen lines, containing only rules whose violation is costly and that the model cannot infer: the process rules that apply to every turn, and an index of what exists in the library with one line each. Put the index in always-on text rather than behind a skill, following Vercel's 100% result and your 3/3, and compress it. Emphasize at most one or two lines, give reasons, and remove contradictions between global and project layers, since conflicts are resolved arbitrarily. Strength: well supported by Anthropic docs and one vendor eval, with one cell of your own; size thresholds are heuristics.

**Inject per turn.** Use UserPromptSubmit (Claude Code) and BeforeAgent (Gemini CLI) to inject the content of the two or three rules that matter for the current state, not a pointer to them. Your 0/4 versus 4/4 supports content over pointer. Keep the text short and state-aware, for example the current workflow stage and its required next artifact, and re-inject after compaction through a SessionStart `compact` matcher. Strength: moderate, from your cell, Spence's results and recap studies on other tasks; cost over long sessions is unknown. For agy, treat per-turn injection as unproven until PreInvocation is tested.

**Workflow step injection.** Have the engine place the step's own instructions, checklists and the skill content directly into the prompt it sends for that step, rather than expecting the agent to fetch skills. This is the same mechanism as the 4/4 cell, applied at step granularity, and it keeps always-on text small. Where a step needs a skill body, preloading it (subagent `skills:` field in Claude Code, or inline text) is better supported than on-demand fetch. Strength: mechanism and your cell support it; no step-level measurement exists.

**Enforce with hooks and gates.** Anything that must hold goes in PreToolUse denial (no commit before tests, no edits outside the step's scope), and completion goes behind a Stop hook or an engine check that runs a script and blocks until it passes, with a `stop_hook_active` guard and awareness of the 8-continuation cap. Let the engine, not the model, decide stage transitions and record them. Use `if` matchers so gates run only on relevant calls. Strength: the deterministic semantics are documented; success rates of Stop gates are unpublished.

**Measure.** Run each rule and skill through a fresh-session harness with positive and negative prompts, 10 or more runs per cell, on each model and each agent you ship, with a no-rule baseline. Assert on the tool-call transcript (was the skill called, did tests run before commit), use an LLM judge only for sequencing, and log cost and latency; use `InstructionsLoaded` to confirm the rule loaded at all. `claude plugin eval` is the first-party option for Claude Code; MLflow's trace-judge layering and Spence's sandbox harness are published templates ([MLflow](https://mlflow.org/blog/evaluating-skills-mlflow)). Re-run on every model change, since Anthropic says prompts are measured on one model and must be re-checked on another.

## Claims that need verifying before anyone relies on them

- Your Haiku 4.5 cells are 3 to 4 prompts each. By my calculation 4/4 versus 0/4 is the only contrast that clearly separates (about p = 0.03, two-sided Fisher), and a 4/4 result is still compatible with a true rate near 50%. Repeat with 10 or more prompts and runs per cell and with the models your users run.
- Whether the 0/4 native plugin skill result reflects Haiku, prompt-to-description mismatch, or a harness fault; and whether an improved description on the MCP fetch tool changes the 1/4.
- Whether the content-carrying reminder still works at turn 30, 100, and after compaction, and what it costs in tokens per session; no published data covers this.
- That UserPromptSubmit-injected reminders are obeyed more reliably than CLAUDE.md in the same position; Anthropic publishes no comparison.
- Whether reminder text injected every turn is eventually ignored or treated as noise (Anthropic's warning about repeated harness text on Sonnet 5.5 suggests a risk).
- The Spence rates (20%, 55%, 84%, 100%) come from one author's harness and the synthetic and real-binary results differ; the "bypasses skills ~80% of the time, 200+ prompts" claim was not traced to a primary source.
- The Vercel result is single-vendor, one framework, with model and agent version unstated.
- The "~50% of sessions" CLAUDE.md violation rate and the 400-line figure are issue-tracker anecdotes. The Augment 100 to 150 line optimum is secondhand.
- The CLAUDE.md wrapper text ("may or may not be relevant") was reported on version 1.0.113 in 2025 and has not been re-verified on the current release.
- Hook limits (10,000 characters, 8 continuations, 30-second timeout) and `tool_choice` restrictions on Sonnet 5.5 and similar come from live docs read via a summarizing fetch; the hooks page was partly read. Check against current behavior, including whether hook output survives compaction.
- Every agy-specific claim: PreInvocation context injection, hook output schema, rule ordering, system-prompt versus user-turn placement of rules, the 24 KB and 20,000-token limits, and the existence of any adherence data. Test directly on the agy version you ship.
- Skill-Use, ToolFailBench and the 2026 instruction-hierarchy papers were read from abstracts or summaries; numbers are unverified and their models are partly open-weight or older.
- The long-context studies (Multi-Turn, IFScale, Chroma, R&R) do not measure coding-agent rule compliance; the transfer is an inference.
- GitHub issue numbers cited for Gemini CLI and Claude Code were read through summaries and mirror sites.
- No evidence was found on how skill count affects activation, on Stop-hook gate success rates, on tool_choice forcing effects, or on emphasis and formatting effects in long runs.

## Conclusion

The practical shift is from asking where a rule should live to asking who decides that it applies. Every approach that leaves the decision to the model (a skill description, a pointer, a fetch tool, a prose prohibition) behaves like a probabilistic suggestion whose reliability falls in long sessions, while approaches that move the decision into the harness (always-on content, injected content, hook denial, engine-controlled stages) behave much better in the available data. That makes the workflow engine, not the skills library, the main reliability lever for Agent World: the library supplies content, and the engine decides when each piece reaches the model.

The weakest point in the evidence is also the one your app depends on most. There is no published study of how well agents obey injected reminders over long, real coding sessions, and almost nothing is measured for agy. The sensible next step is a larger, multi-model version of your own cell experiment, extended to long-session and post-compaction conditions and run on both agents, since this will settle more than further reading will.
