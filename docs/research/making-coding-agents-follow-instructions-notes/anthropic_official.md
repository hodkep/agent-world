# Anthropic official guidance: making Claude Code / Claude follow instructions, rules and skills

Retrieved 2026-10-07. Docs pages are living documents (Claude Code docs reference v2.1.2xx features; model docs reference Sonnet 5.5, Fable 5.1, Opus 5.5). Fetches went through a summarizing fetch tool, so quotes are as returned by it; the long skills and hooks pages were only partly read (first ~100k to 200k chars). Items under Gaps were not verified.

## 1. Why CLAUDE.md / system-prompt instructions may not be followed, and what Anthropic recommends instead

### Takeaway
Anthropic states plainly that CLAUDE.md is advisory context, delivered as a user message after the system prompt, with "no guarantee of strict compliance". Their remedies, in order: shorter files (<200 lines), specific and non-conflicting wording, emphasis on one or two lines only, path-scoped rules or skills for non-universal content, and hooks or permissions for anything that must always happen.

### Cited Findings
- "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead. The more specific and concise your instructions, the more consistently Claude follows them." — [Claude Code memory](https://code.claude.com/docs/en/memory)
- Delivery: "CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself. Claude reads it and tries to follow it, but there's no guarantee of strict compliance, especially for vague or conflicting instructions." — [Claude Code memory, troubleshooting](https://code.claude.com/docs/en/memory)
- Size: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Files over 200 lines trigger a startup warning and a `/status` warning. There is also a warning when files that are each short add up past a combined limit. Hard cap: a CLAUDE.md up to 4 MiB loads in full, larger is skipped. `@path` imports "don't reduce its context cost, because imported files also load at launch". — [memory](https://code.claude.com/docs/en/memory)
- Auto memory `MEMORY.md` loads only the first 200 lines or 25KB, whichever comes first. This is a separate mechanism from CLAUDE.md. — [memory](https://code.claude.com/docs/en/memory)
- Specificity examples: "Use 2-space indentation" over "Format code properly"; "Run `npm test` before committing" over "Test your changes". — [memory](https://code.claude.com/docs/en/memory)
- Conflicts: "if two instructions contradict each other, Claude may pick one arbitrarily". User-level and project-level rules that conflict: "Claude may follow either one". Load order is broad to specific (managed, user, project, local), so instructions closer to the working directory are read last. — [memory](https://code.claude.com/docs/en/memory)
- Best practices page: "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" Test per line: "Would removing this cause Claude to make mistakes? If not, cut it." "If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Emphasis: "If Claude keeps skipping one instruction, add emphasis such as 'IMPORTANT' to that line alone. If you emphasize many lines, none of them stands out." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Failure pattern named by Anthropic: "The over-specified CLAUDE.md... Claude ignores half of it because important rules get lost in the noise. Fix: Ruthlessly prune. If Claude already does something correctly without the instruction, delete it or convert it to a hook." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Include/exclude table: include commands Claude can't guess, style rules that differ from defaults, gotchas. Exclude anything derivable from code, standard conventions, long tutorials, file-by-file descriptions. — [Best practices](https://code.claude.com/docs/en/best-practices)
- Underlying mechanism: "LLM performance degrades as context fills. When the context window is getting full, Claude may start 'forgetting' earlier instructions or making more mistakes." Correct early: after two failed corrections, `/clear` and rewrite the prompt. — [Best practices](https://code.claude.com/docs/en/best-practices)
- Competing built-in guidance: if your CLAUDE.md sets commit or PR rules, turn off the built-in ones with `includeGitInstructions` and set `attribution`. — [memory troubleshooting](https://code.claude.com/docs/en/memory)
- System-prompt-level alternative: "For instructions you want at the system prompt level, use `--append-system-prompt`... better suited to scripts and automation than interactive use." — [memory troubleshooting](https://code.claude.com/docs/en/memory). Managed policy equivalents: managed CLAUDE.md (macOS `/Library/Application Support/ClaudeCode/CLAUDE.md`) or the `claudeMd` key in managed-settings.json. "Settings rules are enforced by the client regardless of what Claude decides to do. CLAUDE.md instructions shape Claude's behavior but are not a hard enforcement layer." — [memory](https://code.claude.com/docs/en/memory)
- Anthropic blog (2026-06-18): "Claude will follow the instruction most of the time, but when under pressure, in a long session or an ambiguous situation... the model can fail to follow a prompted rule." "A real guardrail needs to be deterministic, and the enforcement methods are hooks and permissions." Managed settings are "the only way to enforce a deterministic, organization-wide guardrail." Do not use instructions for "every time X, always do Y" (use hooks), "never do this" (PreToolUse exit 2 or managed settings), or 30-line procedures (use skills). — [Claude blog: Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more) (secondary only in the sense that it's a blog, but first-party Anthropic)
- Persistence: project-root CLAUDE.md is re-read from disk and re-injected after `/compact`. Instructions given only in conversation can be lost. Nested CLAUDE.md and `paths:` rules reload on demand. — [memory](https://code.claude.com/docs/en/memory)
- Debug tools: `/context` lists loaded Memory files; `InstructionsLoaded` hook logs which files load and why; `/doctor prompt-audit` (v2.1.283+) checks for outdated or conflicting instructions; `/doctor` proposes CLAUDE.md trims (v2.1.206+). Audit flags "instructions written for older models". — [memory](https://code.claude.com/docs/en/memory)
- Loading detail: HTML block comments in CLAUDE.md are stripped before injection (free maintainer notes). Subdirectory CLAUDE.md files load only when Read/Write/Edit touches a file there. Path-scoped rules trigger on Read/Write/Edit of matching files, not on every tool use. Subagents load CLAUDE.md by default (`omitClaudeMd` disables). — [memory](https://code.claude.com/docs/en/memory), [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Model-side prompting: models are "trained for precise instruction following". Anthropic says (for Opus 4.5/4.6) that models are "more responsive to the system prompt than previous models... If your prompts were designed to reduce undertriggering on tools or skills, these models may now overtrigger. The fix is to dial back any aggressive language. Where you might have said 'CRITICAL: You MUST use this tool when...', you can use more normal prompting like 'Use this tool when...'." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Fable 5 guide: "Instruction-following is improved enough that you can steer most behaviors with a brief instruction rather than enumerating each behavior by name." Also: "Skills developed for prior models are often too prescriptive for Claude Fable 5 and can degrade output quality. Review and consider removing older instructions." — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- Context rot definition: "As the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases"; "attention budget" framing; system prompts should be at the "right altitude" (specific but not brittle if-else logic); use "the minimal set of information that fully outlines your expected behavior" and add based on observed failures. — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) (2025-09-29)
- Same post on Claude Code design: CLAUDE.md files are dropped into context upfront while glob/grep retrieve just-in-time (hybrid strategy). — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Field evidence (not Anthropic's claims): GitHub issues report CLAUDE.md rules ignored even with MUST/ALWAYS/NEVER or "HARD RULE" wording, e.g. a "NEVER commit unless asked" rule violated. Listed by search, not read in full: [anthropics/claude-code #17530](https://github.com/anthropics/claude-code/issues/17530), [#34197](https://github.com/anthropics/claude-code/issues/34197), [#34774 mirror](https://claudeissues.com/issue/34774-model-claude-code-max-plan-ignores-claude-md-instructions-committed-changes-with). Secondary mirror claims "~50% of sessions" and "~400 lines" are user reports, unverified.

### Inferences
- Anthropic's own docs concede a ceiling on CLAUDE.md adherence; the supported reliability ladder is: concise CLAUDE.md, then path-scoped rules or skills, then `--append-system-prompt` (system-prompt level), then hooks, then permissions/managed settings.
- Because CLAUDE.md arrives as a user message and "closer to cwd is read last", position inside the file and file count matter, but Anthropic gives no numbers beyond the 200-line guidance.
- Heavy emphasis (caps, "HARD RULE") is officially discouraged on newer models because it can overtrigger. Emphasis is recommended only sparingly, on a single line.

### Gaps
- No official quantitative adherence-vs-length curve or percent figures for CLAUDE.md; only the "<200 lines" heuristic. The "30 percent" figure below is for query placement in long prompts, not CLAUDE.md.
- Exact mechanics of how `--append-system-prompt` text is weighted vs CLAUDE.md (system vs user role) are only implied by the troubleshooting text; I did not read the CLI reference page on it.
- GitHub issues were not read in full; no Anthropic maintainer response captured.

## 2. How Agent Skills are discovered and triggered, and making them trigger reliably

### Takeaway
Skills trigger by model judgment: only name and description (plus optional `when_to_use`) sit in context at startup, and Claude matches the task to those. Reliability depends almost entirely on the description (what plus when, key terms, key use case first, under 1,024 chars on the API / 1,536 combined in Claude Code listing). Anthropic gives no guarantee of auto-triggering; explicit `/skill-name` invocation is the deterministic route, and hooks can inject a reminder.

### Cited Findings
- Progressive disclosure, three levels: metadata at startup, SKILL.md body when Claude judges it relevant, linked files only as needed. "At startup, the agent pre-loads the `name` and `description` of every installed skill into its system prompt." Triggering "relies on Claude's judgment about relevance". — [Anthropic Engineering: Equipping agents with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) (2025-10-16)
- "Pay special attention to the `name` and `description` of your skill. Claude will use these when deciding whether to trigger the skill." — same post.
- Description rules (API docs): max 1,024 chars, non-empty, no XML tags; name max 64 chars, lowercase/digits/hyphens, no reserved words "anthropic"/"claude". Write in third person because "The description is injected into the system prompt, and inconsistent point-of-view can cause discovery problems." Include what the skill does and when to use it. Claude "uses it to choose the right Skill from potentially 100+ available Skills." Bad: "Helps with documents". — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Claude Code listing: "Claude uses this to decide when to apply the skill." "Put the key use case first: the combined `description` and `when_to_use` text is truncated at 1,536 characters in the skill listing." Every skill in the listing "adds to your context on every turn, whether or not Claude ever uses it." — [Claude Code skills](https://code.claude.com/docs/en/skills)
- Frontmatter controls (Claude Code): `disable-model-invocation: true` (user-only, description kept out of context), `user-invocable: false` (Claude-only), `paths` (glob limit on activation), `allowed-tools`, `context: fork` plus `agent:`. `skillOverrides` settings: `on` / `name-only` / `user-invocable-only` / `off`. — [skills](https://code.claude.com/docs/en/skills)
- Official troubleshooting for not triggering: (1) description includes keywords users naturally say, (2) skill appears in listing (`/skills`, "What skills are available?"), (3) rephrase to match the description, (4) invoke directly with `/skill-name`. Malformed YAML frontmatter means Claude Code loads the body with empty metadata, so `/skill-name` works but description matching fails (see `--debug`, `claude plugin validate .claude/skills`, v2.1.233+). — [skills](https://code.claude.com/docs/en/skills)
- Over-triggering fixes: more specific description, or `disable-model-invocation: true`. — [skills](https://code.claude.com/docs/en/skills)
- Tooling: `/skill-doctor` shows per-skill context cost and usage frequency and flags never-used skills. Plugin skills can be eval'd with `claude plugin eval` using a `tool_used: Skill` grader to "measure how often it triggers across realistic prompts". — [skills](https://code.claude.com/docs/en/skills)
- Skill after invocation: content enters as one message and stays; Claude Code does not re-read the file on later turns, so write guidance as "standing instructions rather than one-time steps". After compaction, the most recent invocation of each skill is re-attached, first 5,000 tokens each, combined budget 25,000 tokens, most recent first (older skills can be dropped). — [skills](https://code.claude.com/docs/en/skills)
- Skill body: keep SKILL.md under 500 lines; reference files one level deep; add a table of contents to reference files over 100 lines (Claude may `head -100` nested files). Match "degrees of freedom" to fragility: exact scripts for fragile operations ("Run exactly this script... Do not modify the command"). Use scripts for deterministic steps; feedback loops (validate, fix, repeat); checklists to avoid skipped steps ("Clear steps prevent Claude from skipping critical validation"). — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Prominence: Anthropic's own iteration example says Claude A may suggest "using stronger language such as 'MUST filter' instead of 'always filter'" when a rule is missed in a skill. Conflicts mildly with the later "dial back aggressive language" guidance for newer models; both are Anthropic docs. — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); [prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Features-overview framing: "If descriptions are vague or overlap, Claude may load the wrong skill or miss one that would help. To tell Claude to use a specific skill, invoke it with `/<name>`." Also: too many extensions add noise, "skills may not trigger correctly". — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Subagent analogue: Claude delegates by matching the subagent `description`; add "use proactively" to encourage it. `@agent-name` mention "guarantees invocation"; `--agent` / `agent` setting for session-wide default. Combined subagent descriptions should stay under about 15,000 tokens. — [Sub-agents](https://code.claude.com/docs/en/sub-agents)
- Field evidence (users, not Anthropic): multiple GitHub issues report skills ignored even when request exactly matches description, and ignored despite "BLOCKING REQUIREMENT" wording in CLAUDE.md: [#20986](https://claudeissues.com/issue/20986-claude-ignores-skill-triggers-even-when-user-request-clearly-matches-skill-descr), [#19308](https://claudeissues.com/issue/19308-critical-claude-systematically-ignores-skill-tool-despite-explicit-blocking-requ), [#15136](https://claudeissues.com/issue/15136-bug-claude-fails-to-invoke-skills-immediately-despite-explicit-instructions). Over-triggering also reported: [#83557](https://claudeissues.com/issue/83557-claude-api-skill-over-triggers-on-any-claude-model-mention-injecting-400k-tokens). Mirror site, not read in full. A third-party blog also exists ([Scott Spence](https://scottspence.com/posts/claude-code-skills-dont-auto-activate)); secondary.

### Inferences
- Anthropic offers no hard guarantee for auto-trigger; the deterministic paths are `/skill-name`, subagent `skills:` preload, `@agent` mention, or a hook that injects "use skill X" context.
- With many installed skills, descriptions compete for attention and budget; trimming, `name-only`, or `disable-model-invocation` are the sanctioned levers.
- Trigger reliability should be measured, not eyeballed: `claude plugin eval` with a `tool_used: Skill` grader is the only first-party mechanism found.

### Gaps
- I did not confirm any published trigger-rate numbers for skills, or the exact overall skill-listing character budget across all skills (docs hint at a truncation/"descriptions are cut short" section, not read in full; last ~4k chars of the skills page unread).
- Anthropic's `anthropics/skills` repo README/issues were not fetched.

## 3. Hooks: injecting and enforcing behavior

### Takeaway
Hooks are the only deterministic layer. SessionStart and UserPromptSubmit can inject text (stdout or `additionalContext`, capped at 10,000 chars each, arrives as a system reminder); PreToolUse can deny; Stop can force Claude to continue (with an 8-consecutive-continuation default cap); HTTP hooks work via JSON response bodies, not status codes.

### Cited Findings
- Cadences: per session (`SessionStart`, `SessionEnd`), per turn (`UserPromptSubmit`, `Stop`, `StopFailure`), per tool call (`PreToolUse`, `PostToolUse`). Hooks "merge: all registered hooks fire". Handler types: command, http, mcp_tool, prompt (LLM), agent (subagent). — [Hooks reference](https://code.claude.com/docs/en/hooks), [features overview](https://code.claude.com/docs/en/features-overview)
- SessionStart: matchers `startup`, `resume`, `clear`, `compact`, `fork`. Output `hookSpecificOutput.additionalContext` is "added to Claude's context at the start of the conversation, before the first prompt"; also `initialUserMessage`, `sessionTitle`, `watchPaths`, `reloadSkills`. Plain stdout also reaches Claude. Hooks run in the background but "Claude's first response still waits for the hooks to finish, so their context reaches Claude." Firing on `compact` makes it a way to re-inject rules after compaction. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- UserPromptSubmit: fires "when a prompt is submitted, before Claude processes it" (also on turns Claude Code starts itself). Input has `prompt`. Output: plain stdout or JSON `additionalContext`; "Plain stdout and the `additionalContext` value are each injected as a system reminder that starts with the hook's name; Claude reads both." No visible transcript entry. Can block: `{"decision":"block","reason":...}` or exit 2 ("blocks the prompt, so it never reaches Claude"). `suppressOriginalPrompt` and `sessionTitle` also exist. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Limits: "A hook's `additionalContext`, `systemMessage`, and `initialUserMessage` strings, and its plain stdout, are capped at 10,000 characters" measured per string even if several hooks run. Over the limit: saved to a file in the session dir, replaced by path plus first 2,000 chars preview. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Timeouts: default 600 s for command/http/mcp_tool, 30 s for prompt, 60 s for agent; lowered to 30 s on `UserPromptSubmit` (and Pre/PostModelSwitch), 10 s on `MessageDisplay`; SessionEnd shares a 1.5 s budget. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Exit codes: exit 0 = success, stdout shown to Claude only for UserPromptSubmit, UserPromptExpansion, SessionStart, PostModelSwitch (others go to debug log). Exit 2 = blocking: on PreToolUse blocks the call, on UserPromptSubmit blocks the prompt, on Stop "Prevents Claude from stopping, continues the conversation"; "even a JSON `permissionDecision` of `allow` can't override it." PermissionRequest ignores exit 2. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- PreToolUse: `hookSpecificOutput.permissionDecision` of `allow|deny|ask|defer`, `permissionDecisionReason`, `updatedInput` (rewrite tool input), `additionalContext`. Precedence when multiple hooks disagree: `deny` > `defer` > `ask` > `allow`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Stop: input has `stop_hook_active`, `last_assistant_message`, `background_tasks`, `session_crons`; `stop_hook_active` is true when already continuing due to a stop hook. Block via `decision: "block"` + `reason` (reason is fed back to Claude), exit 2 with stderr as reason, or `additionalContext` for non-error feedback. Cap: "8-consecutive-continuation cap" then Claude Code ends the turn; count resets when Claude calls a tool; raise via `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`. SubagentStop has the same control. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Universal output: `continue: false` stops Claude entirely with `stopReason`; `systemMessage` is a user-facing warning. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- HTTP hooks: fields `url`, `headers` (env interpolation only for names in `allowedEnvVars`), `timeout`. Response: 2xx empty body = success; 2xx JSON = same schema as command hooks; 2xx other body = non-blocking error; non-2xx = non-blocking error; timeout = canceled. "Unlike command hooks, HTTP hooks can't signal a blocking error through status codes alone" so return 2xx with JSON decision fields. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- `InstructionsLoaded` hook: observability only (no blocking); fires for CLAUDE.md, not for AGENTS.md read via the setting. — [Hooks reference](https://code.claude.com/docs/en/hooks), [memory](https://code.claude.com/docs/en/memory)
- When to use hooks: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." "An instruction like 'never edit `.env`' in CLAUDE.md or a skill is a request, not a guarantee. A `PreToolUse` hook that blocks the edit is enforcement." Context cost of hooks is "Zero, unless the hook returns additional context". — [Best practices](https://code.claude.com/docs/en/best-practices), [features overview](https://code.claude.com/docs/en/features-overview)
- Verification gate pattern: ask in prompt, set a `/goal` condition (separate evaluator re-checks each turn), or "a Stop hook runs your check as a script and blocks the turn from ending until it passes", or a fresh-context verification subagent. "A reviewer prompted to find gaps will usually report some, even when the work is sound" (tell it to flag only correctness/requirement gaps). — [Best practices](https://code.claude.com/docs/en/best-practices)
- A SessionStart hook that prints AGENTS.md is called out as a workaround to remove once Claude reads AGENTS.md directly (duplicate context). Confirms hook-injected instructions are an accepted pattern. — [memory](https://code.claude.com/docs/en/memory)

### Inferences
- A UserPromptSubmit hook injecting a short reminder (for example "check for a matching skill; run TDD") is within official capability (10k chars, 30 s default timeout, delivered as a system reminder) and is deterministic in delivery, though Claude's compliance with the reminder is still model-decided. Only block/deny/exit-2 paths are enforcement.
- The Stop-hook pattern can force continuing until a check passes, bounded by the 8-continuation cap. Hook must check `stop_hook_active` or exit when the condition is met to avoid hitting the cap.
- Per-turn injection costs tokens every turn (the injected text lands in context each time); SessionStart injection is once per session but must be repeated on `compact` via matcher.

### Gaps
- Read only the first ~200k of the 250k-char hooks page; the hooks-guide page was not fetched. Not verified: whether injected reminders are deduplicated across turns or how they are retained through compaction.
- No published data on how reliably the model obeys hook-injected `additionalContext` vs CLAUDE.md.

## 4. Subagents, slash commands, plugins, output styles as delivery routes

### Takeaway
Anthropic positions each as a different loading strategy: CLAUDE.md always-on, rules path-scoped, skills on-demand (model or user triggered), subagents isolated context, plugins as packaging, output styles for tone/format. Only hooks and permissions enforce.

### Cited Findings
- Comparison table: CLAUDE.md "Every request" cost; output styles every request; skills "Low (descriptions every request)"; MCP low until used; subagents isolated; hooks zero unless output. — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Skills vs CLAUDE.md: "Rule of thumb: Keep CLAUDE.md under 200 lines. If it's growing, move reference content to skills or split into `.claude/rules/`." — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Layering: CLAUDE.md additive (conflicts reconciled by "judgment"); skills/subagents override by name (managed > user > project for skills); MCP override by name; hooks merge. — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Output styles: for "a voice, length, or format you want in every response"; "Claude follows both [CLAUDE.md and output style] as instructions, so neither is enforced." — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Subagents get their own system prompt (not Claude Code's), the delegation prompt, and CLAUDE.md hierarchy (except Explore/Plan); `skills:` field fully preloads skill content into the subagent at launch (instead of on-demand). Subagents have their own `hooks` frontmatter. Forks inherit the parent conversation and system prompt. — [Sub-agents](https://code.claude.com/docs/en/sub-agents), [features overview](https://code.claude.com/docs/en/features-overview)
- Independent verification: a reviewer in a fresh subagent context "sees only the diff and the criteria you give it, not the reasoning that produced the change". Fable 5 guide: "Separate, fresh-context verifier subagents tend to outperform self-critique." — [Best practices](https://code.claude.com/docs/en/best-practices), [Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- Plugins "bundle skills, hooks, subagents, and MCP servers into a single installable unit"; plugin skills are namespaced `/plugin:skill`. — [Best practices](https://code.claude.com/docs/en/best-practices), [features overview](https://code.claude.com/docs/en/features-overview)
- Slash commands and skills are merged in Claude Code: a skill is invocable as `/name` and `disable-model-invocation` makes it user-only (the old commands directory is covered by the same system; `/doctor prompt-audit` scans "rules, skills, commands, subagents, and output styles"). — [skills](https://code.claude.com/docs/en/skills), [memory](https://code.claude.com/docs/en/memory)
- Managed distribution: org-wide managed CLAUDE.md (cannot be excluded via `claudeMdExcludes`), or `claudeMd` key in managed settings; these load before user and project CLAUDE.md. — [memory](https://code.claude.com/docs/en/memory)

### Inferences
- For a user whose global CLAUDE.md is long and also depends on skills, the officially sanctioned structure is: tiny always-on CLAUDE.md, path rules for scoped items, skills for procedures, hooks for must-always steps, subagent or Stop-hook verification for definition-of-done gates.

### Gaps
- Plugin-specific behavior for hook/skill precedence and the `claude plugin eval` report format were not read beyond the skills page excerpt.
- Did not fetch the legacy `.claude/commands` doc; merge-with-skills behavior is inferred from skills page wording.

## 5. Prompting guidance for instruction adherence (placement, length, emphasis, XML, examples, long context, tool descriptions, tool_choice)

### Takeaway
Be explicit and literal, give the reason, use XML sections and 3 to 5 diverse examples, put long data first and the query/instructions last (up to 30% quality gain in Anthropic's tests), avoid shouting on current models, write detailed tool descriptions (the single most important factor), and use `tool_choice` any/tool only where supported; the cost is about 120 extra system-prompt tokens plus no pre-tool text and cache invalidation.

### Cited Findings
- "Claude responds well to clear, explicit instructions"; golden rule: show the prompt to a colleague with minimal context; "If they'd be confused, Claude will be too." Use sequential numbered steps when order matters. — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Give the why: "Providing context or motivation behind your instructions... can help Claude better understand your goals." Example: replace "NEVER use ellipses" with the text-to-speech reason; "Claude is smart enough to generalize from the explanation." Fable 5 guide echoes "Give the reason, not only the request". — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), [Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- Positive over negative: "Tell Claude what to do instead of what not to do." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Examples: "one of the most reliable ways to steer"; make them relevant, diverse, structured in `<example>`/`<examples>` tags; "Include 3 to 5 examples for best results." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- XML tags: wrap each content type (`<instructions>`, `<context>`, `<input>`) with consistent descriptive names to reduce misinterpretation; nest where hierarchical. Effective context engineering post also allows Markdown headers. — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), [context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Long context (20k+ tokens): "Put longform data at the top... above your query, instructions, and examples." "Queries at the end can improve response quality by up to 30 percent in tests, especially with complex, multidocument inputs." Ask Claude to quote relevant parts first. — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Match prompt style to desired output style (removing markdown from the prompt reduces markdown in output). — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Explicit action wording: "Can you suggest some changes" yields suggestions; "Change this function" yields edits. Provided `<default_to_action>` and `<do_not_act_before_instructions>` system-prompt blocks to set default proactivity. — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Agentic snippets from Anthropic: verification (`Before you finish, verify your answer against [test criteria]`), reversibility/confirmation guidance, anti-overengineering, no hardcoding to tests, `<investigate_before_answering>`, context-window/compaction reassurance to stop early wrap-up. Caveat: on Opus 5, verification instructions from older prompts "can cause over-verification". — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Sonnet 5.5 specifics: add the "Keep working until everything the user asked for is done, and only stop to ask when you can't go on without the user or before a risky step" paragraph to reduce check-ins at low/medium effort (sessions run longer and cost more); a "run a real check that exercises the change before reporting it done" paragraph makes skipped checks "rare" at low effort. At medium+ effort "Asking it in the system prompt to think less doesn't reliably reduce its thinking." Harness text injected after every tool result can be read as prompt injection; deliver mid-turn user text as a user turn, keep reminders infrequent. — [Prompting Claude Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)
- Fable 5: audit-claims-against-tool-results instruction "nearly eliminated fabricated status reports" in Anthropic testing; state boundaries explicitly; avoid showing token countdowns. — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- Thinking-related: do not instruct the model to reproduce its reasoning in output on Fable 5.x / Sonnet 5.5 (can trigger `reasoning_extraction` refusal); ask for a short explanation instead. — [Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5), [Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- Prompt-vs-model-version: "treat it as measured on that model and re-check it against your own evals before applying it to another." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Tool descriptions: "Provide extremely detailed descriptions. This is by far the most important factor in tool performance": what it does, when to use (and not use) it, parameter meaning, caveats; "at least 3 to 4 sentences". Consolidate related operations into fewer tools; namespace names; return high-signal responses; optional `input_examples` (adds about 20 to 50 tokens simple, 100 to 200 complex). — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Engineering post: "small refinements to tool descriptions can yield dramatic improvements" (cited: Sonnet 3.5 SWE-bench Verified); describe a tool "how you would describe your tool to a new hire"; evaluate with realistic multi-call tasks tracking accuracy, runtime, tool calls, tokens, errors; read transcripts, as "what agents omit... can often be more important". — [Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (2025-09-11)
- Tool clarity: "If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better." — [context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Steering `auto` triggering by prompt: "Use the tools to investigate before responding" increases tool use; "Always call a tool first before responding" pushes further; "Use your judgment..." keeps it conservative. With `auto`, "Claude determines on each turn whether to call a tool or respond directly." — [Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)
- `tool_choice` options: `auto` (default with tools), `any` (must use one of the tools), `tool` (forces a named tool), `none`. With `any`/`tool` "the API prefills the assistant message to force a tool to be used", so "the models will not emit a natural language response or explanation before `tool_use` content blocks, even if explicitly asked"; Anthropic says testing "should not reduce performance". For text plus forced tool, use `auto` with an explicit user instruction ("Use the get_weather tool in your response."). — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Restrictions (as of fetch): manual extended thinking (`type: enabled`) rejects `any`/`tool`; Opus 5.5, Sonnet 5.5, Fable 5.1, Mythos 5.1 return 400 for `any`/`tool`. Alternatives: `auto` with strict tool use (`strict: true`) or structured outputs; prompting still influences which tool `auto` picks. Adaptive thinking itself doesn't block forced tool use on Opus 5. This matters because the current model (Sonnet 5.5) cannot be forced to call a tool via API. — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Token tradeoff: tool-use system prompt tokens (when `tools` present) auto/none vs any/tool: Opus 5 286 vs 406; Opus 4.8 290 vs 410; Sonnet 5 354 vs 474; Sonnet 4.6/Opus 4.6 497 vs 589; Haiku 4.5 496 vs 588; Opus 4.7 675 vs 804; Sonnet 5.5 and Opus 5.5 286 for auto/none, any/tool column blank (unsupported). Plus tokens for the `tools` parameter (names, descriptions, schemas), `tool_use` and `tool_result` blocks. `tool_choice: none` with no tools costs 0 extra. Changing `tool_choice` invalidates cached message blocks (tools and system prompt stay cached). — [Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview), [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Overcorrection warning: "If in doubt, use [tool]" instructions cause overtriggering on newer models; replace blanket defaults with targeted ones. — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

### Inferences
- In Claude Code the model chooses `auto` throughout; an "invoke the Skill tool first" requirement can only be pushed via text (CLAUDE.md, append-system-prompt, hook-injected reminder), not via `tool_choice`, and on Sonnet 5.5 not even via the raw API.
- Wording like "CRITICAL / HARD RULE" is the pattern Anthropic says to dial back on current models; short, reasoned, specific rules plus one emphasized line is the sanctioned style.
- Placement guidance (queries last) is documented for long documents; for CLAUDE.md the only placement statement is load order (closer scope read later).

### Gaps
- No official number for how long a system prompt/CLAUDE.md can be before adherence drops beyond "<200 lines".
- Did not fetch the `strict-tool-use`, `effort`, or `mid-conversation-system-messages` pages; the turn-scoped system message beta is referenced in the Sonnet 5.5 page and might be relevant to reminder injection in API harnesses (not Claude Code).

## 6. Published guidance on evaluating skill / instruction adherence

### Takeaway
Anthropic recommends evaluation-driven development (baseline without the skill, at least three scenarios, test across Haiku/Sonnet/Opus, observe real runs), and Claude Code now ships first-party measurement (`/skill-doctor`, `claude plugin eval` with a Skill-tool grader, `/doctor prompt-audit`, `InstructionsLoaded` hook). No official benchmark numbers for instruction adherence were found.

### Cited Findings
- Build evaluations first: identify gaps by running without a Skill, create three scenarios, establish a baseline, write minimal instructions, iterate. Example eval JSON has `skills`, `query`, `files`, `expected_behavior`. Note: "There is not currently a built-in way to run these evaluations" (API-side doc). Checklist: "At least three evaluations created; Tested with Haiku, Sonnet, and Opus". — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Observe how Claude navigates: unexpected read order, missed references, overreliance on some files, ignored content. "Iterate based on these observations rather than assumptions." Claude A (author) / Claude B (tester) loop. Team feedback: "Does the Skill activate when expected?" — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Engineering post: "Start with evaluation: Identify specific gaps in your agents' capabilities by running them on representative tasks and observing where they struggle." — [Agent Skills post](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- First-party tooling in Claude Code: `claude plugin eval` with `tool_used: Skill` grader to "measure how often it triggers across realistic prompts"; `/skill-doctor` for cost and usage; `claude plugin validate` for frontmatter parse errors; `/doctor prompt-audit` for stale/conflicting instruction files. — [skills](https://code.claude.com/docs/en/skills), [memory](https://code.claude.com/docs/en/memory). A plugin-evals page is linked from skills (`/docs/en/plugin-evals`), not fetched.
- CLAUDE.md as code: "review it when things go wrong, prune it regularly, and test changes by observing whether Claude's behavior actually shifts." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Tool eval methodology (metrics list, transcript review) — [Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Model docs: re-check prompts against own evals when changing models; "re-evaluate which instructions, tools, and guardrails are still needed" after capability jumps. — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), [Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)
- Evidence-of-completion practice: "Have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned, or a screenshot." — [Best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- An adherence eval for a rule set could be built from `claude plugin eval` (Skill triggered?) plus transcript graders checking for required behaviors, run per model; this is the closest first-party method.
